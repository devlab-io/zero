## Run 2 (même journée) — recherche projection-first (obs 3, reliquat serveur)

Objectif : « premier résultat <1 s » sur la voie mesurée par la CUA (palette →
Entrée → `q` → Gmail, 2,24 s observées). Deux coûts identifiés sur cette voie,
deux correctifs, sémantique Gmail préservée.

### Coût amont révélé (client) : détour IA systématique

`command-palette-dialog.tsx` : `handleSearch(query, true)` — la voie par défaut
de la touche Entrée — appelait TOUJOURS `ai.generateSearchQuery` (aller-retour
OpenAI) AVANT même de poser `searchValue`, y compris pour une phrase littérale
comme « Banque de Tahiti ». Le 2,24 s mesuré INCLUT donc ce détour.

Correctif : **bypass déterministe** (`lib/search-intent.ts`,
`isSimpleLiteralSearch`) — une requête littérale simple part immédiatement en
recherche exacte (voie `useNaturalLanguage=false` existante, chips/filtres/
recherches récentes identiques) ; l'IA est CONSERVÉE pour les opérateurs Gmail,
les dates (12/03, années, mois en/fr), les mots d'intention (en/fr), les
négations et booléens. Asymétrie assumée : un littéral classé « naturel » =
statu quo (lent, correct) ; un naturel classé « littéral » = recherche
plein-texte Gmail sur les mots tapés (résultats raisonnables, non réécrits).
30 cas de classification testés.

### Contrat serveur : préview projection, Gmail authoritatif

La projection DO savait déjà chercher (`findThreadsWithTextSearch` /
`findThreadsWithPagination` avec `searchText`, LIKE sur `latest_subject` +
`latest_sender`, scope label du dossier) — `mail.ts` ne l'exposait simplement
pas pour `q`. **Blocage sémantique réel et assumé : la projection ne couvre pas
le corps des messages ni les opérateurs Gmail — elle NE PEUT PAS remplacer
Gmail `q`.** Le plus petit contrat sûr retenu :

1. `listThreads` accepte `localPreview: boolean` (défaut false, rétrocompatible).
   `q + localPreview` → projection DO (sous-ensemble strict du scope Gmail :
   même label de dossier, LIKE sujet/expéditeur). Requête à opérateurs ou à
   jokers LIKE (`%`/`_`, vivants dans un LIKE SQLite sans ESCAPE) →
   `previewSearchText` renvoie '' → page vide (jamais un faux « résultat »).
2. Le client (`use-threads.ts`) lance la préview EN PARALLÈLE de la recherche
   Gmail. Pendant le vol Gmail : les correspondances préview remplacent la vue
   précédente (`selectSearchPreviewItems`) ; préview vide → fallback comportement
   run 1 (vue précédente + bandeau) — jamais de « aucun résultat » précoce sur la
   seule foi de la projection. Bandeau « Recherche en cours » maintenu pendant
   tout le vol.
3. Gmail atterri : ses lignes (ordre et composition authoritatifs) reprennent
   l'affichage ; les fils déjà servis par la préview greffent leurs champs
   riches sur les lignes minces (`enrichThinItemsWithPreview`) — pas de flip
   vers un squelette ; les fils hors préview (correspondance dans le corps)
   gardent le fetch par ligne existant.
4. Hold forceSync prioritaire sur la préview (pas de substitution pendant la
   fenêtre de resynchro).

### Revue de risques du diff run 1 (voie recherche)

- `keepPreviousData` + préview : composition saine via `isPlaceholderData`
  (préview seulement pendant le vol ; l'atterrissage Gmail la révoque).
- Échec de la query préview (500, shard) → `data` undefined → fallback
  silencieux run 1. Aucun couplage avec la query authoritative.
- `%`/`_` dans le texte agissent comme jokers LIKE (paramètre lié, pas
  d'injection SQL) car la projection interroge SQLite en LIKE **sans clause
  ESCAPE** — un `%` littéral aurait affiché presque tous les fils avant Gmail,
  soit un faux résultat que le contrat interdit. **Fermé (revue post-run 2)** :
  `previewSearchText` rejette tout texte contenant `%` ou `_` → page vide →
  fallback client (pas de préview = sûr). SQLite ne connaît aucun autre
  métacaractère LIKE (pas de classes `[...]`, ESCAPE inactif non déclaré).
  `findThreadsWithTextSearch` (voie MCP préexistante, hors contrat préview)
  garde son comportement.
- LIKE SQLite : insensible à la casse ASCII seulement (accents sensibles) —
  une préview manquée = fallback, jamais un résultat faux.
- Multi-shards : `getThreadsFromDB` concatène sans tri global (préexistant,
  aggregator `server-utils.ts`) — ordre de préview possiblement approximatif
  sur topologie multi-shards ; l'ordre final est toujours celui de Gmail.
- Aucun risque nouveau détecté dans le diff run 1 lui-même (bandeau, flag,
  keepPreviousData inchangés et exploités tels quels).

## Incident d'environnement documenté (harness de test)

L'ajout d'un **second site d'appel** `import()` du même module mocké
(préchauffe + factory `React.lazy`, dans le même tick) fait perdre le mock à
vitest 3.2.7 par intermittence : le module réel s'évalue et le test de contrat
palette échouait (`No "useParams" export…`). Corrigé **dans le code produit**
par la promesse d'import mémoïsée (un seul appel réel, pattern souhaitable en
soi), plus un flush déterministe (`vi.waitFor`) dans le test — contrat
inchangé. À savoir pour tout futur préchargement d'un module aussi consommé
par `React.lazy`.
